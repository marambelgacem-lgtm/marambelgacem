FIELD NOTES / PRIVILEGE ESCALATION

CTF 1 ( Valley ctf : on TryHackMe)

this was my first ctf on THM ..the write up will be explained in steps

1. INTRODUCTION :

This challenge provides the IP address of a target machine. The first step is to identify its open ports and available services.

Using RustScan:

rustscan -a <IP>

RustScan quickly identifies open ports on the target.

Alternatively, we can use Nmap:

nmap -A -p- -T4 -Pn <IP>

⚠ Breakdown

Options:

  • -A: Enables OS detection, service-version detection, script scanning, and traceroute.
  • -p-: Scans TCP ports 1–65535.
  • -T4: Uses an aggressive timing template.
  • -Pn: Skips host discovery and treats the target as online.

The notes list these ports:

  • 80: HTTP.
  • 22: SSH.
  • 443: HTTPS.
  • 37370 [confirm]: initially unidentified.

At this stage, I focused on the web service running on port 80 and began web enumeration.

2. WEB ENUMERATION

Web enumeration involves investigating a website and discovering hidden files, directories, and endpoints.

I used Gobuster:

gobuster dir -u http://<IP>/ -w /usr/share/dirb/wordlists/common.txt -x php -r

⚠ Breakdown

Understanding the wordlist path:

  • /usr/: Contains system-wide programs, libraries, and shared resources.
  • share/: Shared application data.
  • dirb/: Resources associated with DIRB.
  • wordlists/: Lists of potential directory and file names.
  • common.txt: A wordlist of common names such as admin, login, and robots.txt.

The -x php option adds .php to the candidate names during enumeration.

The scan revealed directories including:

/pricing
/gallery

I explored them but did not find anything useful.

Another directory caught my attention:

/static/

I performed another scan against it:

gobuster dir -u http://<IP>/static -w raft-medium-directories.txt -x php,sh,html,txt,js

Note: The full local path to the wordlist is not recorded.

raft-medium-directories.txt is a wordlist from SecLists. The -x option appends the specified extensions to each candidate name.

3. DISCOVERING A DEVELOPMENT LOGIN

After the scan, I investigated:

/static/00

Its response was much smaller than the others, which made it worth examining.

The notes then lead to a development directory containing a login form:

/dev[ numeric suffix]folder

I performed another enumeration against this directory. Among the four entries discovered, one was particularly useful:

dev.js

Inspecting this JavaScript file revealed a username and password.

These credentials worked for FTP, but not for SSH.

4. ACCESSING FTP AND DOWNLOADING FILES

FTP, or File Transfer Protocol, transfers files between a client and a server.

After logging in, I listed the available files:

ls -la

I found three .pcapng packet-capture files and downloaded them to my Kali machine.

To download one file:

get <filename>

To download multiple files:

mget <files>

5. ANALYZING THE CAPTURES WITH WIRESHARK

I opened the downloaded captures in Wireshark.

The useful information was in:

siemHTTP2.pcapng

This capture contained another set of credentials.

A useful Wireshark feature is Follow TCP Stream, which reconstructs the conversation between a client and a server.

I tested the recovered credentials against:

  • SSH.
  • FTP.
  • The web application.

Only SSH accepted them.

6. FINDING THE USER FLAG

After connecting to the target through SSH, I explored the files and read the user flag using:

ls
cat <user-flag-file>

With the user flag obtained, the next objective was to gain root access through privilege escalation.

7. INVESTIGATING AUTOMATED TASKS

I began by examining automated tasks, particularly those running as root.

I checked the permissions of a relevant script:

ls -la

My current user could read and execute it but could not modify it.

After inspecting its code, I identified a possible privilege-escalation route involving its use of Python’s base64 module.

8. LOCATING THE PYTHON MODULE

To locate the module, I used:

find / -name '*base64*'

The notes identify this file:

/usr/lib/python3.8/base64.py

My current user could not modify it. However, the notes indicate that members of the valleyAdmin group had write access.

The valley user belonged to that group, but I had not yet gained access to that account.

I also found a program named:

valleyAuthenticator

I decided to inspect it.

9. EXAMINING valleyAuthenticator

I used SCP to copy the program to my local machine.

SCP securely copies files between computers. The completed command structure is:

scp <current-user>@<IP>:/home/valleyAuthenticator .

I then examined printable strings inside the binary:

strings valleyAuthenticator

⚠ Breakdown

The strings command extracts readable text from a binary, which can reveal messages or embedded credential-related information.

According to the notes, this revealed an MD5 hash associated with the valley account’s password.

After recovering the password, I switched accounts:

su valley

10. MODIFYING THE PYTHON MODULE

With access to the valley account, I could modify the module:

nano /usr/lib/python3.8/base64.py

I added the following lines at the beginning:

import os
os.system('chmod +s /bin/bash')

⚠ Breakdown

What this does:

  • import os gives the script access to Python’s operating-system interface.
  • os.system(...) executes the supplied shell command.
  • The command changes special permission bits on /bin/bash. The intended effect is to allow Bash to run with its owner’s privileges.

This technique depends on the root-run task importing the modified module, causing the added code to execute with root privileges.

11. OBTAINING ROOT ACCESS

After the privileged task executed the modified module, I ran:

/bin/bash -p

The intended result was a Bash shell that retained elevated privileges.

I then located and read:

root.txt
